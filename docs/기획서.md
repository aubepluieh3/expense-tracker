# Personal Expense Tracker — 기획서

> 최종 갱신: 2026-07-28
> 설계 문서: `docs/설계.md`

---

## 1. 개요

### 1.1 무엇을 만드나

개인 가계부 웹 서비스. 수입·지출을 기록하고 월 단위로 조회·분석한다.

### 1.2 목적

| 목적 | 내용 |
|---|---|
| 실사용 | 만든 사람이 직접 매일 쓰는 것이 1차 목표 |
| 학습 | 회원가입·인증 흐름을 직접 구현해 보는 것 |

### 1.3 사용자

회원가입을 제공하는 **다중 유저 서비스**. 단, 실사용자는 소수를 전제한다.

### 1.4 플랫폼

반응형 웹 (SPA). 모바일 브라우저를 우선 대상으로 하고 데스크톱도 지원한다.

## 2. 기술 스택

| 영역 | 선택 |
|---|---|
| 프레임워크 | Vite + React + TypeScript |
| 스타일 | Tailwind CSS |
| 인증 · DB | Supabase (PostgreSQL + Auth + RLS) |
| 서버 상태 | TanStack Query |
| 차트 | **없음** — div + CSS (§6.5) |
| 날짜 | 자체 유틸 (`src/lib/month.ts`) |
| 배포 | Cloudflare Pages (프론트) + Supabase (무료 티어) |

### 선택 근거

- **백엔드 서버 코드를 작성하지 않는다.** 브라우저의 `supabase-js`가 PostgreSQL을 직접 호출하고, 사용자별 데이터 격리는 DB의 RLS 정책이 강제한다. API 서버·ORM·인증 구현이 통째로 사라진다.
- **Next.js를 쓰지 않는다.** 로그인 뒤에서 동작하는 개인용 도구라 SSR도 SEO도 필요 없다.
- **Firestore가 아닌 PostgreSQL.** 이 앱의 핵심은 월별·카테고리별 집계다. `GROUP BY` 한 줄로 끝나는 일을 NoSQL에서는 전체 문서를 읽어 클라이언트에서 합산해야 한다.

### 반응형 전략

**데스크톱 전용 레이아웃을 만들지 않는다.**

```
모바일    화면 꽉 채움 + 하단 고정 탭 + 우하단 FAB
데스크톱  max-width 520px 중앙 정렬 카드 + 컬럼 상단 탭 + 툴바 "＋ 추가"
```

가계부는 세로로 긴 목록이 본체라 넓은 화면을 줘도 쓸 데가 없다. 2단 레이아웃은 작업량을 두 배로 만들면서 얻는 것이 여백뿐이다.

**데스크톱에서 FAB 을 쓰지 않는다.** 뷰포트 하단 고정이라 화면이 세로로 길어지면 스크롤 위치와 무관하게 목록 중간을 덮는다 — 실제로 금액과 날짜 소계가 가려졌다. 큰 화면에서는 월 네비게이터 옆 툴바 버튼으로 대체한다.

**데스크톱에서는 페이지 배경을 한 단계 낮추고 컬럼에 테두리를 준다.** 흰 배경에 흰 컬럼이면 어디까지가 앱 영역인지 알 수 없다.

## 3. 기능 명세

### 3.1 회원가입 / 로그인

| 항목 | 내용 |
|---|---|
| 가입 정보 | 이메일, 비밀번호, 닉네임 |
| 비밀번호 | 최소 8자 |
| 이메일 인증 | **있음** — 메일 확인 후 로그인 가능 |
| 소셜 로그인 | 없음 |
| 비밀번호 재설정 | **있음** (비로그인 상태) |
| 비밀번호 변경 | **있음** (로그인 상태, 설정 화면의 시트) |
| 회원 탈퇴 | 없음 |
| 로그인 유지 | Supabase 기본값 (토큰 자동 갱신) |

**비밀번호 관련 흐름은 두 가지다**

| 상황 | 경로 |
|---|---|
| 로그인 못 함 | `/forgot-password` → 메일 링크 → `/reset-password` |
| 로그인 상태에서 바꾸고 싶음 | 설정 → 비밀번호 변경 |

전자만 있어도 데이터 소실은 막는다. 후자는 여유가 되면 넣는다.

**가입 흐름**

```
/signup 제출
  → auth.users 생성 (이 시점에 프로필·기본 카테고리 자동 생성)
  → 세션은 아직 없음
  → 같은 화면에서 "메일을 확인해 주세요  [다시 보내기]" 로 전환
  → 메일 링크 클릭 → 앱으로 복귀, 세션 생성 → 홈
```

**로그인 실패 메시지**

| 상황 | 메시지 |
|---|---|
| 비밀번호 틀림 / 없는 계정 | `이메일 또는 비밀번호가 올바르지 않습니다` |
| **미인증 계정** | `이메일 인증이 필요합니다`  + **[인증 메일 다시 받기]** |

전자는 계정 존재 여부를 감추기 위해 통일한다. 후자는 예외다 — 통일해 버리면 비밀번호가 맞는데도 계속 틀렸다고 나와서 **사용자가 영원히 로그인할 수 없다.** 계정 노출을 감수하더라도 막다른 골목을 만들지 않는 쪽을 택한다.

**비밀번호 입력은 "표시" 토글로 처리한다.** 확인 필드는 입력을 두 배로 만들면서 복붙으로 무력화되지만, 표시 토글은 필드 하나로 오타를 실제로 잡는다.

> **비밀번호 재설정과 이메일 인증은 한 세트다**
> 재설정 없음 + 회원 탈퇴 없음 + 내보내기 없음이 겹치면 비밀번호를 잊는 순간 데이터가 영구 소실된다. 그래서 재설정을 넣었는데, **재설정은 유효한 이메일을 전제로 한다.** 인증이 없으면 오타 주소(`hong@gmial.com`)로 가입한 사용자에게 재설정 메일이 도달하지 않아 구멍이 그대로 남는다. 둘 중 하나만 넣으면 의미가 없다.

### 3.2 수입·지출 등록

**거래 필드 (5개)**

| 필드 | 규칙 |
|---|---|
| 금액 | 원화 **정수**, 0보다 큼. 소수점·다중 통화 없음 |
| 날짜 | **날짜만** (시간 없음). 기본값 오늘. **미래 날짜 허용** |
| 수입/지출 구분 | 기본 선택은 **지출** |
| 카테고리 | **필수**. 선택한 구분에 해당하는 카테고리만 노출 |
| 메모 | 선택. 최대 100자 |

**규칙**

- 날짜를 `date` 로만 저장하므로 타임존 경계 문제가 발생하지 않는다.
- 금액은 항상 양수로 저장한다. 부호는 수입/지출 구분이 결정한다.
- 미래 날짜 거래도 해당 월 집계에 포함한다. 단 월급 위젯에서는 제외한다 (§3.6).

### 3.3 거래 수정 / 삭제

- 등록 화면을 그대로 재사용하고 값만 채워서 연다.
- **삭제는 완전 삭제**. 확인 다이얼로그를 띄운다.
- 과거 거래도 제한 없이 수정 가능하다 (마감 개념 없음).
- 수입 ↔ 지출 전환을 허용한다. 전환 시 카테고리 선택은 초기화된다 (타입이 분리되어 있으므로).

### 3.4 카테고리 설정

**구조**

| 항목 | 규칙 |
|---|---|
| 소유 | 사용자별 |
| 타입 | **수입용 / 지출용 분리** |
| 계층 | 없음 (평면 구조) |
| 개수 | **제한 없음** |
| 이름 | 같은 타입 안에서 중복 금지 (삭제된 것 포함) |
| 이모지 | 1자. 중복 허용. 미선택 시 기본값 `📦` |
| 색 | 8슬롯 **자동 배정, 1~8 순환**. 사용자가 고르지 않음 |
| 급여 카테고리 | 사용자당 1개를 지정 (월급 위젯 기준, §3.6) |

**기본 카테고리 (가입 시 자동 생성)**

```
지출 (6)   🍚 식비    ☕ 카페·간식   🚌 교통
           🏠 주거·통신 🛒 생활용품    🎬 문화·여가

수입 (4)   💼 급여    💰 용돈       📈 금융수입   📦 기타수입
```

`💼 급여` 가 급여 카테고리로 지정된다. 지출을 6개만 주는 이유는, 안 쓰는 기본 카테고리를 정리하는 것도 사용자 작업이고 칩 그리드에 안 쓰는 항목이 섞이면 오히려 선택이 느려지기 때문이다. 필요한 것은 직접 추가한다.

#### 삭제 — 사용자에게는 개념이 하나뿐이다

**하드 삭제냐 소프트 삭제냐는 구현 디테일이며 UI에 노출하지 않는다.** 사용자에게 보이는 동작은 "삭제" 하나다.

```
[삭제] 누름
  → 거래가 있으면 안내:
     "'헬스'를 삭제합니다.
      기록된 거래 23건과 과거 통계는 그대로 유지됩니다."
  → 목록에서 사라짐
  → 하단 스낵바 5초:  "'헬스'를 삭제했습니다.   [실행 취소]"
```

- 내부적으로는 **항상 소프트 삭제**한다. 완전 삭제하면 실행 취소가 불가능해지는데, 어떤 경우에만 실행 취소가 되는 것은 일관성이 없다.
- 삭제된 카테고리는 새 거래에서 선택할 수 없다.
- **과거 통계에는 원래 이름·이모지·색 그대로 남는다.**
- 카테고리 관리 화면에 "숨긴 카테고리" 같은 목록을 두지 않는다.

#### 되살리기

복구 UI를 상시 노출하지 않고, **사용자가 복구를 떠올리는 유일한 순간**에 배치한다.

```
＋ 추가 → 이름 '헬스' 입력 → 저장
  ↓
"예전에 삭제한 '헬스'가 있습니다.
 되살리면 과거 거래 23건이 다시 연결됩니다."

 [ 되살리기 ]      또는 다른 이름을 입력하세요
```

**"새로 만들기" 선택지는 제공하지 않는다.** 같은 이름의 카테고리가 둘 생기면 사용자가 화면에서 구별할 방법이 없어진다 (§9 참조).

되살릴 때 **색 슬롯은 원래 값을 유지**한다. 슬롯 순환을 허용하므로 중복 검사가 없고, 따라서 과거 통계의 색이 항상 그대로 보존된다.

**두 층의 안전망**

| 시점 | 수단 |
|---|---|
| 삭제 직후 (실수) | 스낵바 **실행 취소** 5초 |
| 한참 뒤 (다시 필요) | 같은 이름 입력 시 **되살리기 제안** |

> **왜 '미분류로 이동'이 아닌가**
> 개인 가계부에서는 "지금은 안 쓰지만 작년엔 썼던" 카테고리가 계속 생긴다(이직 전 교통비, 자취 시절 월세). 미분류로 옮기면 작년 통계가 "미분류 40만원"으로 뭉개진다. 삭제를 차단하면 오타로 만든 카테고리가 영원히 남는다. 소프트 삭제만이 "목록에서는 치우되 기록은 보존"을 만족한다.

### 3.5 월별 내역 조회

| 항목 | 규칙 |
|---|---|
| 기간 축 | **달력월 (1일 ~ 말일)** |
| 월 상태 | **URL 쿼리** (`?month=2026-07`) — 통계 화면과 공유 |
| 정렬 | 날짜 내림차순 |
| 그룹핑 | 날짜별. 헤더 우측에 그날 소계 표시 |
| 미래 날짜 | 오늘 이후 날짜 그룹에 **`예정` 배지**. 월급 위젯이 미래 지출을 따로 빼는 것과 기준을 맞춘다 |
| 페이징 | 없음 (한 달치 전체 로드) |
| 필터 | 수입/지출 토글 + 카테고리 **단일** 선택 |

**카테고리 필터 목록은 "그 달에 거래가 있는 카테고리"로 채운다**

활성 카테고리로 채우면 안 된다. 삭제된 카테고리의 과거 거래를 필터로 찾을 방법이 사라지기 때문이다 — 3월 내역에 '헬스' 거래가 5건 보이는데 필터 목록에는 '헬스'가 없는 상태가 된다. 부수 효과로 그달에 안 쓴 카테고리가 목록에서 빠져 선택도 짧아진다.

**필터는 목록에만 적용한다.** 상단 요약(수입/지출/남은 금액)은 항상 그 달 전체를 보여준다.

> 요약까지 필터에 반응하면 "남은 금액"이 의미 없는 숫자가 된다 (식비만 걸었는데 남은 금액이 −420,000원).

필터 적용 시 목록 위에 `🍚 식비 · 12건 · 420,000원 ✕` 요약 칩을 띄운다.

**월 상태를 URL에 두는 이유**

새로고침해도 보던 달이 유지되고, 브라우저 뒤로가기가 달 이동으로 정상 동작하며, 특정 달을 북마크할 수 있다. 전역 상태로 관리하는 것보다 코드도 적다.

### 3.6 월별 총수입 / 총지출 / 남은 금액

**정의**

```
남은 금액 = 그 달의 총수입 − 총지출
```

- 라벨은 **"남은 금액"**. "잔액"이라고 쓰지 않는다 — 통장 잔고로 오해한다.
- 근거를 함께 표시한다: `수입 320만 · 지출 124만`

**💼 월급 위젯 (홈 상단)**

사용자의 실제 질문인 "이번 월급 얼마 남았지?"에 직접 답하는 위젯.

| 항목 | 규칙 |
|---|---|
| 기준 | **급여 카테고리로 지정된 카테고리**의 가장 최근 수입 거래 1건 |
| 계산 | `마지막 급여 금액 − 그 이후 지출 합계` |
| 집계 범위 | **오늘까지.** 미래 거래는 제외 |
| 미래 거래 | 있으면 `예정 지출 1,200,000` 을 별도 줄로 표시 |
| 표시 | 남은 금액, 진행 바, 지급일, 다음 급여까지 남은 일수 |
| 다음 급여일 | `마지막 급여일 + 1개월` |
| 급여 거래 없음 | 빈 상태 — "급여를 등록하면 남은 금액을 보여드려요" |
| 급여 등록 누락 | `마지막 급여 6.25 · 34일 전` 을 함께 표시해 인지시킴 |

**급여 카테고리는 사용자 프로필이 카테고리 id를 참조하는 방식으로 지정한다.**

이름(`'급여'`)으로 찾으면 안 된다. 사용자가 '월급'이나 '수임료'로 바꾸는 순간 위젯이 조용히 죽고, 원인을 알 방법이 화면에 없다. 이름은 사용자가 언제든 바꾸는 표시용 라벨이지 시스템의 식별자가 아니다.

"이 카테고리가 급여인가"는 카테고리의 속성이 아니라 **사용자의 설정**이다. 그래서 카테고리가 아니라 프로필이 갖는다. 지정 변경은 프로필 한 행 수정으로 끝나고, "사용자당 1개"가 컬럼 하나라는 사실만으로 보장된다.

**지정 변경 UI**: 수입 카테고리 수정 화면에 `☑ 월급 위젯 기준으로 사용` 토글 하나. 지출 카테고리 화면에는 이 항목이 없다. 프리랜서가 '수임료'를 지정하거나, 급여 카테고리를 지운 사용자가 다른 것으로 옮길 수 있다.

> **급여일을 별도로 설정받지 않는 이유**
>
> 급여일을 사용자 설정으로 두고 기간 축 자체를 급여 사이클로 바꾸는 안을 검토했으나 폐기했다.
>
> - 기간 라벨이 대부분의 날에 틀린다. 급여일이 25일이면 `6.25~7.24` 를 "6월"이라 부르게 되는데, 사용자는 7월 20일에도 화면에서 "6월"을 본다 (한 기간의 80%).
> - 급여일을 바꾸면 과거 기간 경계가 전부 재계산되어 지난달에 본 숫자가 오늘 달라진다. 막으려면 급여일 이력 테이블이 필요하다.
>
> **집계 축(달력월, 불변)과 관점(월급 사이클, 가변)을 분리**하면 두 문제가 동시에 사라진다. 급여 거래의 날짜가 곧 급여일이므로 **거래 기록 자체가 급여일 이력**이 된다. 3월엔 25일, 7월엔 10일에 받았어도 그대로 남는다.

### 3.7 카테고리별 지출 통계

| 항목 | 규칙 |
|---|---|
| 대상 | **지출만** |
| 기간 | 달력월. 내역 화면과 **월 공유** (URL) |
| 형태 | 상단 100% 스택 바 + **가로 막대 목록** (금액 내림차순) |
| 표시 | 카테고리별 금액 + 비율 |
| 개수 | **상위 7개 + "기타"**. 기타는 탭하면 펼쳐짐 |
| 색 | 순위 기반 단일 색조 램프 (§6.3). 기타는 무채색 |
| 막대 길이 | **최댓값 기준** 정규화. 이 화면의 용도가 순위 판별이라서 |
| 비교 | 총 지출 옆에 `지난달 대비 +12% ↑`. 색은 쓰지 않는다 |
| 연결 | 막대 행을 탭하면 해당 카테고리로 필터된 내역으로 이동 |
| 하단 | `앱 사용 이후 누적 +4,280,000원` (전체 수입 − 전체 지출) |

**"기타" 행은 회색 · 흐린 글씨 · % 없음**으로 그린다. 항목이 아니라 묶음인데 다른 행과 같은 무게로 그리면 동급으로 읽히고, 내림차순 목록에서 순서가 어긋나 보인다(기타 합계가 7위보다 클 수 있다).

**지난달 지출이 0이면 증감 표시를 생략한다.** `0원 → 120만원` 을 "+∞%" 라고 쓰는 것은 정보가 아니다.

```
이번 달 지출
1,240,000원   지난달 대비 +12% ↑
███████████░░░░░░░░░░░░

🍚 식비   ██████ 420,000 34%
🏠 주거   ████   280,000 23%
🚌 교통   ███    180,000 15%
☕ 카페   ██     120,000 10%
📦 기타   ▌      150,000 11%
```

**삭제된 카테고리도 그대로 나온다.** 통계 쿼리는 카테고리의 삭제 여부를 보지 않는다. 이것이 "과거 통계 보존"의 구현이다.

> **파이 차트를 쓰지 않는 이유**
>
> - 사람은 각도·면적을 정확히 비교하지 못한다. 34%와 30% 조각의 우열을 눈으로 판별할 수 없다. 길이는 정확히 본다.
> - 사용자가 통계를 켜는 이유는 "어디에 제일 많이 썼지?"인데, 파이는 그 답을 정렬해서 주지 않는다.
> - 카테고리가 8개만 돼도 조각이 실처럼 얇아지고 한글 라벨을 밖으로 빼야 한다.
> - 조각과 범례를 색으로만 연결하므로 색각 이상 사용자가 읽을 수 없다.
>
> 가로 막대는 **색이 없어도 길이가 정보를 전달한다.** 파이가 잘하던 "전체 중 얼마"는 100% 스택 바 한 줄이 더 정확히 준다.

> **"누적"을 통장 잔고라고 부르지 않는 이유**
> 초기 자산을 입력받지 않으므로 실제 잔고를 알 수 없다. "앱 사용 이후 모은 돈"이라는 정직한 의미로 두면 초기 자산 설정 기능이 불필요해진다.

## 5. 화면

### 5.1 구조

```
로그인  /  회원가입  /  비밀번호 재설정          (비로그인)
──────────────────────────────────────────
📋 내역   ← 기본 화면                            하단 탭 3개
   └ 거래 등록 / 수정  (모달)
📊 통계
⚙️ 설정
   └ 카테고리 관리
```

### 5.2 내역 (홈)

```
┌──────────────────────────────────────────┐
│  ‹        2026년 7월        ›    ⏷  ＋추가│  ← ＋추가는 데스크톱만
│  💼 월급 남은 돈       3,200,000원 중 61% │
│  1,960,000원                              │
│  ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░                     │
│  6.25 지급 · 다음 급여까지 3일 · 예정 8,000│
├──────────────────────────────────────────┤
│  7월 남은 금액  수입 320만·지출 124만  +1,960,000│
├──────────────────────────────────────────┤
│  7월 30일 (목) 예정                −8,000│
│   ☕ 카페·간식                      −8,000│
│  7월 3일 (목)                     −13,400│
│   🍚 식비                         −12,000│
│      점심 김밥천국                         │
│   🚌 교통                          −1,400│
│  7월 2일 (수)                             │
│   💼 급여                      +3,200,000│
└──────────────────────────────────────────┘
                                   ( ＋ )  ← 모바일만
```

**규칙**

- 상단은 **6줄**이다. 월 네비 1 + 월급 위젯 4 + 월 요약 1. 처음에는 8줄이라 거래가 4건만 보였는데, 위젯을 접는 컨트롤을 새로 만들기보다 줄을 합치는 편이 낫다 — 지급일·다음 급여·예정 지출을 한 줄로, 월 요약도 한 줄로 줄였다.
- 월 라벨을 탭하면 월 선택 시트가 열린다 (`‹ ›` 만 있으면 6개월 전으로 가는 데 6번 눌러야 한다). 라벨은 `1fr auto 1fr` 그리드로 **컬럼 정중앙**에 둔다 — flex 로 하면 오른쪽 버튼이 있는 화면에서만 라벨이 밀려서 탭을 옮길 때 튄다.
- 필터는 **깔때기 아이콘 하나**로 접어 둔다. 사용자의 대부분은 "전체"로 본다. 필터가 걸렸을 때만 요약 칩이 나타난다.
- 날짜 헤더 우측에 **그날 소계**를 흐리게 표시한다. 오늘 이후 날짜에는 `예정` 배지.
- **모바일**: `＋` FAB 을 하단 탭 위 16px에 띄우고 목록 끝에 80px 여백을 둔다. 안 하면 마지막 거래가 가려진다.
- **데스크톱**: FAB 을 쓰지 않고 툴바의 `＋ 추가` 버튼을 쓴다 (§2 참조).

### 5.3 거래 등록 / 수정

```
┌──────────────────────────────┐
│  ✕      지출 등록       저장  │
├──────────────────────────────┤
│       [ 지출 ]   수입         │
├──────────────────────────────┤
│  최근                         │
│   🍚    ☕    🐶             │
│  식비  카페  반려             │
│                               │
│   🍚    ☕    🚌    🏠       │
│  식비  카페  교통  주거       │
│   🛒    🎬    🐶   ⋯ 더보기  │
│  생활  문화  반려             │
├──────────────────────────────┤
│  금액             12,000 원   │
│  날짜  [어제][오늘]  7.3  📅  │
│  메모  점심 김밥천국          │
└──────────────────────────────┘
```

**이 화면이 가장 중요하다.** 가계부가 버려지는 1위 원인은 기능 부족이 아니라 입력 귀찮음이다.

| 규칙 | 이유 |
|---|---|
| **저장 버튼은 상단 우측** | 하단 고정 버튼은 모바일 키보드에 반드시 가린다. 웹에서 키보드 위로 버튼을 밀어올리려면 `visualViewport` 를 다뤄야 한다 |
| **카테고리를 금액보다 위에** | 키보드가 필요 없는 선택을 먼저 끝낸다. 금액을 먼저 치면 키보드가 카테고리 그리드를 가린다 |
| **카테고리는 칩 그리드** | 드롭다운은 `열기→스크롤→선택` 3동작, 그리드는 1동작 |
| **최대 8개 노출 + 더보기** | 그리드가 화면을 다 먹지 않도록. 카테고리 개수 자체에는 제한이 없다. `더보기` 도 한 칸이므로 칩은 7개까지만 그려 4열 두 줄에 맞춘다 |
| **그리드 순서는 생성순 고정** | 사용 빈도순·최근순으로 그리드를 재정렬하면 위치가 계속 바뀌어 근육 기억이 안 생긴다. 위치가 고정돼야 안 보고 누른다 |
| **그리드 위에 `최근` 3칸을 따로** | 반복 입력을 줄이면서 그리드는 건드리지 않는 방법. 아래 그리드와 겹쳐 보여도 그대로 둔다 |
| **지출이 기본 선택** | 거래의 대부분은 지출이다 |
| **날짜에 [어제][오늘] 퀵 버튼** | 실제 입력의 대부분이 이 둘. 달력은 예외 경로 |
| **메모는 맨 아래, 선택** | 위에 두면 매번 뭘 써야 할 것 같은 압박이 생긴다 |
| **금액에 숫자 키패드** | `inputmode="numeric"` |

**선택된 칩은 배경 · 링 · 글자 굵기 세 채널로 표시한다.** 처음에는 10% 검정 배경 + 1px 링뿐이라 실제 화면 크기에서 어느 칩이 선택됐는지 보이지 않았다(3배로 확대해야 겨우 보였다). 검정 배경으로 칠하지 않는 이유는 이모지가 자체 색을 가진 그림이라 어두운 배경에서 대비가 무너지기 때문이다 — `🚌` `🎬` 같은 어두운 이모지가 묻힌다.

**`최근` 줄을 그리드 위에 따로 둔 이유.** 사용성 테스트에서 한 주치를 몰아 입력해 보니 같은 카테고리를 반복해 고르는 구간이 있었다. 자연스러운 해법은 "칩을 최근 사용순으로 정렬"인데, 그러면 저장할 때마다 그리드 전체가 재배치된다. 자주 쓰는 두세 개가 서로 앞자리를 왕복하므로 **가장 많이 쓰는 구간이 가장 불안정해진다.** 익숙한 자리를 안 보고 누른 사람은 다른 카테고리로 저장하고도 알 수 없다 — 에러는 나지 않고 통계만 틀어진다. 8개 노출 구조에서는 어제 1번이던 칩이 오늘 `더보기` 뒤로 숨는 일도 생긴다.

그래서 **재정렬 범위를 3칸으로 격리했다.** 그리드는 움직이지 않고, `최근`이라는 줄의 위치 자체는 고정이라 그 줄에도 근육 기억이 생긴다. 직접 추가해 `더보기` 뒤로 밀린 카테고리도 한 번 쓰면 윗줄로 올라온다 — 애초에 노리던 케이스가 이것이다.

정렬 기준은 거래의 `created_at`(입력 시각)이지 `occurred_on`(거래 날짜)이 아니다. 주말에 지난주를 몰아 적으면 방금 입력한 카테고리의 `occurred_on` 이 며칠 전이라 최근 목록에서 뒤로 밀린다. 사람이 "최근에 쓴 것"으로 느끼는 건 손이 마지막으로 누른 것이다.

**수정 화면**은 같은 화면을 재사용하고 하단에 삭제 버튼만 추가한다. 입력 중 `✕` 를 누르면 확인을 받는다.

### 5.4 통계

§3.7 참조. 월 네비게이터는 내역 화면과 **동일한 컴포넌트**를 쓴다.

### 5.5 설정 / 카테고리 관리

```
[설정]
  닉네임 / 이메일
  카테고리 관리          ›
  비밀번호 변경          ›
  로그아웃

[카테고리 관리]
  ┌ 지출 │ 수입 ┐
  🍚 식비              │ 수정  삭제
  ☕ 카페·간식          │ 수정  삭제
  ...
  ＋ 카테고리 추가
```

삭제된 카테고리 목록은 **표시하지 않는다.** 사용자는 삭제했다고 인식하는데 목록이 남아 있으면 "지웠는데 안 지워진" 느낌을 준다. 되살리기는 §3.4의 두 안전망으로 처리한다.

### 5.6 빈 / 로딩 / 에러 상태

가입 직후 사용자가 처음 보는 화면은 **텅 빈 내역 목록**이다. 첫인상이므로 빠뜨리지 않는다.

| 상태 | 처리 |
|---|---|
| 거래 0건 | `📝 아직 기록이 없어요 / 첫 지출을 기록해 볼까요? [기록 시작하기]` |

## 6. 시각 규칙

### 6.1 색의 역할 분리

이 앱에는 색을 요구하는 축이 둘 있다 — **카테고리(분류)** 와 **수입/지출(성격)**. 둘 다 색으로 칠하면 화면이 시끄러워지고 둘 다 안 읽힌다.

```
카테고리   → 이모지 (사람이 읽는 식별자). 색은 쓰지 않는다
지출 순위  → 색 (통계 화면 전용, 단일 색조 램프)
수입/지출  → 부호(+/−) 와 금액 글자색만
```

- 수입 금액: `+` 와 초록 (`#006300`)
- 지출 금액: `−` 와 기본 글자색. **빨갛게 칠하지 않는다** — 목록 대부분이 빨개져서 강조가 사라진다.

### 6.2 접근성 원칙

**색만으로 정보를 전달하지 않는다.** 카테고리 이름 텍스트는 항상 함께 표시한다. 색은 빠르게 훑을 때 눈이 걸리는 보조 역할까지만 맡는다.

### 6.3 통계 색 — 순위 기반 단일 색조 램프

통계 화면의 색은 **카테고리 고유색이 아니라 지출 순위**를 나른다. 파랑 한 색조의 진 → 연 램프이고, 항목 수에 맞춰 고르게 훑는다.

```
#184f95  #1c5cab  #256abf  #2a78d6  #3987e5  #5598e7  #6da7ec  #86b6ef
진함 ←──────────────── 지출 순위 ────────────────→ 옅음

#b8b8b3  "기타" — 팔레트 밖 무채색
```

가장 옅은 단계도 흰 배경에서 2:1 대비를 넘는다.

> **왜 카테고리마다 다른 색을 주지 않는가**
>
> 처음에는 8색 팔레트를 카테고리에 고정 배정했다. "카테고리를 색으로 구별해야 한다"는 전제였는데, 실제로 만들어 보니 **이모지와 이름이 이미 정체성을 담당**하고 있었다. 색이 그 일을 맡지 않으면 색은 다른 정보를 나를 수 있고, 그게 순위다.
>
> 부수 효과가 크다. 무지개가 사라져 화면이 정돈되고, 순위가 색으로도 읽혀 정보가 늘고, **"카테고리가 8개를 넘으면 색이 부족하다"는 문제 자체가 사라진다.**
>
> `categories.color_slot` 컬럼은 남아 있지만 화면 어디에서도 읽지 않는다. 나중에 카테고리 고유색이 필요해질 여지가 있어 지우지 않았다.

### 6.4 사용자가 색을 고르지 않는 이유

애초에 고를 것이 없다. 카테고리에는 색이 없고, 통계 색은 순위에서 자동으로 나온다. 사용자가 고르는 것은 이모지 하나뿐이다.

### 6.5 차트 라이브러리를 쓰지 않는 이유

그리는 것이 **사각형 두 종류**(100% 스택 바, 가로 막대)뿐이다. 축·격자·툴팁·좌표 변환이 없으므로 차트 라이브러리가 값을 하는 지점이 없다.

`div` 로 만들면 라운딩·세그먼트 간격·진입 애니메이션·hover 강조·한글 truncate 를 CSS 로 그대로 통제할 수 있고, 막대를 누르는 인터랙션도 그냥 `<button>` 이다. 번들도 90kB(gzip) 절약된다.

설계 초기에 recharts 를 고른 것은 **파이 차트를 만들 계획이었기 때문**이다. 파이를 철회하면서 라이브러리 선택을 다시 보지 않은 누락이었다. 나중에 시간축 라인 차트(월별 추이) 같은 것이 필요해지면 그때 넣으면 된다.

### 6.6 타이포그래피

**본문 폰트는 Pretendard.** `index.html` 의 `<link>` 로 로드하고 `--font-sans` 토큰으로 지정한다.

이 앱은 **화면의 절반이 숫자**다. 그래서 한글 인상보다 숫자 모양과 폭이 선택 기준이었다.

| 왜 Pretendard 인가 | |
|---|---|
| 숫자 폭이 고르다 | 금액이 세로로 정렬되는 목록에서 자리가 흔들리지 않는다 |
| 한글·라틴 크기가 맞는다 | `7월 3일 · −12,000` 에서 기준선이 어긋나지 않는다 |
| dynamic subset | `unicode-range` 92조각 중 화면에 나온 글자가 든 것만 내려온다 (실측 10파일 ~40KB). 통째로 받으면 1MB 를 넘는다 |

**탈락한 후보**

- **Noto Sans KR** — 숫자 높이가 한글보다 작아 나란히 두면 내려앉아 보이고, 12px 보조 텍스트가 흐리다. 서브셋 조각이 없어 통째로 내려온다.
- **Wanted Sans** — Pretendard 와 사실상 쌍둥이(64px 샘플에서 2px 차이). 후보로 나란히 둘 이유가 없었다.
- **IBM Plex Sans KR** — 숫자에 개성이 있지만 기계적이어서 가계부의 인상과 거리가 있다.

선언이 없던 동안에는 OS 마다 다른 폰트로 보였다 — Windows 맑은 고딕 / macOS Apple SD 산돌고딕 / Android Roboto+Noto. **내가 만든 화면을 내가 본 대로 남에게 보여줄 수 없는 상태**였다.

**글자 크기는 역할 4개 + hero 로 고정한다.**

| 토큰 | 크기 | 쓰는 곳 |
|---|---|---|
| `text-hero` | 24px | 위젯·통계 대표 숫자 |
| `text-body` | 15px | 목록 항목·금액·입력 |
| `text-label` | 14px | 라벨·버튼·설명문 |
| `text-caption` | 12px | 보조 수치·배지 |

이전에는 9종이 쓰였고, 특히 `text-sm`(14px)과 `text-[15px]`이 같은 역할로 섞여 있었다.

### 6.7 디자인 토큰과 프리미티브

**값을 고르는 게 아니라 역할을 고른다.** Tailwind v4 의 `@theme` 블록에 토큰을 정의하고, 화면 코드는 토큰만 쓴다.

```
잉크    ink · ink-2 · ink-muted
면      surface · surface-2 · surface-3 · selected
선      line (목록 구분선) · line-2 (카드·입력 테두리)
강조    accent · accent-hover        ← 강조색은 하나뿐이다. 검정.
의미색  income · danger · danger-soft
라운딩  radius-control(10) · radius-card(16) · radius-sheet(20)
```

**프리미티브**

| 컴포넌트 | 역할 |
|---|---|
| `Button` | primary · outline · ghost · danger × block · inline |
| `TextLink` · `SubtleButton` | 문장 안 링크 / 행 안 부수 동작 |
| `Callout` | error · notice — 모든 에러·안내 박스 |
| `List` + `rowClass` | 목록 4곳의 행 높이·구분선·이모지 크기 |
| `TextField` · `PasswordField` | 입력. 클래스가 한 곳에만 있다 |
| `Sheet` | 항상 `✕ \| 제목 \| (액션)` 헤더 |

> **왜 토큰 계층이 필요했나**
>
> 이 블록이 없던 동안 42개 파일의 유틸 1001개를 전부 호출 지점에서 골랐다.
> 그 결과 글자 색이 `neutral-400·500·600·700` 네 단계로, 라운딩이 5종으로,
> 버튼 모양이 5가지로 흩어졌다. 특히 **같은 "에러"인데 폼은 빨간 박스, 목록
> 로딩 실패는 배경 없는 회색 텍스트**여서 목록 쪽이 "디자인이 안 먹은 것"처럼
> 보였다.
>
> 반복되는 클래스 조합은 **뽑아내지 않은 컴포넌트가 있다는 신호**다.
> `font-medium text-ink underline` 이 4곳, 행 안 부수 동작이 4곳에 반복돼 있었고
> 각각 `TextLink` · `SubtleButton` 이 됐다.

**행의 내용이 화면마다 다른 목록은 컴포넌트로 묶지 않고 클래스만 공유한다.** 거래·카테고리·설정·통계 네 목록을 하나의 `ListRow` 로 추상화하면 어느 것도 제대로 맞지 않는다.

## 9. 결정 이력 요약

주요 판단과 근거만 모았다. 상세는 각 절에 있다.

| 결정 | 대안 | 선택 이유 |
|---|---|---|
| 달력월 축 + 월급 위젯 | 급여 사이클 전면 전환 | 라벨 정확성과 과거 데이터 안정성을 동시에 얻는다 |
| 가로 막대 | 파이 차트 | 순위가 읽히고, 색 없이도 정보가 전달된다 |
| 소프트 삭제 (UI는 "삭제" 하나) | 삭제 차단 / 미분류 이동 / 삭제·숨김 2개념 | 목록은 정리하면서 과거 통계를 보존하고, 사용자가 배울 개념은 늘리지 않는다 |
| 카테고리 개수 무제한 | 색 슬롯 수만큼 제한 | 시각 제약이 도메인 규칙을 정하면 안 된다 |
| 되살리기만 제공 (새로 만들기 없음) | 동명 카테고리 허용 | 이름이 중복되면 사용자가 화면에서 두 카테고리를 구별할 수 없다 |
| 급여 카테고리를 프로필의 id 참조로 지정 | 이름('급여')으로 식별 / 카테고리에 플래그 | 이름은 식별자가 아니다. 그리고 이건 카테고리의 속성이 아니라 유저의 설정이다 |
| 이모지 식별자 | 아이콘 셋 / 색상만 | 아이콘 자산 없이 인지 속도가 올라간다 |
| Supabase 직접 호출 | 자체 API 서버 | 인증·격리·집계가 전부 해결되고 서버 코드가 0줄이다 |
| 비밀번호 재설정 포함 | 제외 | 없으면 비밀번호 분실 시 데이터가 영구 소실된다 |
| 이메일 인증 켜기 | 끄기 | 비밀번호 재설정은 유효한 이메일을 전제로 한다. 둘 중 하나만 넣으면 의미가 없다 |
| 통계 색 = 순위 램프 | 카테고리 고유 8색 | 이모지·이름이 이미 정체성을 담당한다. 색을 풀어주면 순위를 나를 수 있고, 개수 제한 문제도 사라진다 |
| 차트 라이브러리 없음 | recharts | 사각형 두 종류뿐이라 축·툴팁·좌표 변환이 필요 없다. CSS 통제력과 번들 90kB |
| 데스크톱은 상단 탭 + 툴바 버튼 | 하단 탭 + FAB 공용 | FAB 이 뷰포트 하단 고정이라 긴 화면에서 목록 중간을 덮었다 |
| 미래 거래에 `예정` 배지 | 표시 없음 | 월급 위젯은 미래 지출을 따로 빼는데 목록에서 섞여 있으면 기준이 어긋난다 |
| 오늘 날짜를 클라이언트가 넘김 | DB `current_date` | Supabase DB 타임존이 UTC 라서 KST 오전 0~9시에 하루가 밀린다 |
| `최근` 3칸을 그리드 위에 따로 | 칩 그리드를 최근 사용순으로 재정렬 | 그리드를 재정렬하면 자주 쓰는 두세 개가 앞자리를 왕복해 가장 많이 쓰는 구간이 가장 불안정해진다. 오탭은 에러 없이 통계만 틀어진다 |

### 동명 카테고리를 허용하면 생기는 문제

"새로 만들기"를 제공하지 않는 근거다. 삭제된 `A: 헬스`와 새 `B: 헬스`가 공존할 때:

| 증상 | 심각도 |
|---|---|
| A에 도달할 경로가 사라져 되살릴 수도 지울 수도 없는 유령이 된다 | 🔴 탈출 불가 |
| 필터가 B로 걸려서, 화면에 보이던 A의 거래가 사라진다 | 🔴 구별 수단 없음 |
