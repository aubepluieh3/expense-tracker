# Personal Expense Tracker — 설계

> 최종 갱신: 2026-07-28
> 기획: `docs/기획서.md`

---

## 1. 전체 구조

```
브라우저 (Vite + React SPA)
    │
    │  supabase-js  (인증 · 쿼리 · RPC)
    ▼
Supabase
    ├─ Auth          이메일/비밀번호, 메일 인증, 비밀번호 재설정·변경
    └─ PostgreSQL    테이블 3개 + RLS + 함수 7개 + 트리거 2개
```

**차트 라이브러리를 쓰지 않는다.** 통계 화면이 그리는 것은 사각형 두 종류(100% 스택 바, 가로 막대)뿐이라 축·격자·툴팁·좌표 변환이 없다. `div` + CSS 로 만든다 (기획서 §6.5).

**백엔드 서버 코드는 없다.** 브라우저가 PostgreSQL을 직접 호출하고, 사용자별 격리는 RLS가 강제한다.

## 2. 데이터 모델

### 2.1 관계

```
auth.users  (Supabase 관리)
    │
    ├──1:1──▶ profiles ──salary_category_id──▶ categories
    ├──1:N──▶ categories ◀──category_id── transactions
    └──1:N──▶ transactions
```

### 2.2 `profiles`

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `id` | `uuid` | NO | — | PK. `auth.users.id` 와 동일 |
| `nickname` | `text` | NO | — | 표시 이름 (1~20자) |
| `salary_category_id` | `uuid` | YES | `NULL` | 월급 위젯 기준 카테고리 |

```sql
PRIMARY KEY (id)
FOREIGN KEY (id) REFERENCES auth.users(id) ON DELETE CASCADE
FOREIGN KEY (salary_category_id, id) REFERENCES categories (id, user_id)
CHECK (char_length(nickname) BETWEEN 1 AND 20)
```

- 이메일·비밀번호·가입 시각은 `auth.users` 가 갖는다. 중복 저장하지 않는다.
- **복합 FK `(salary_category_id, id)`** — `profiles.id` 가 곧 `user_id` 이므로, 이 제약이 남의 카테고리를 가리키는 것을 DB에서 차단한다.
- `ON DELETE` 절을 두지 않는다(`NO ACTION`). 카테고리는 항상 소프트 삭제이므로 이 FK가 발동할 일이 없다.
- `salary_category_id` 가 `NULL` 이거나 가리키는 카테고리가 삭제 상태면 월급 위젯은 빈 상태를 표시한다.

### 2.3 `categories`

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `id` | `uuid` | NO | `gen_random_uuid()` | PK |
| `user_id` | `uuid` | NO | — | 소유자 |
| `type` | `text` | NO | — | `'income'` \| `'expense'` |
| `name` | `text` | NO | — | 이름 (1~20자, 정규화됨) |
| `emoji` | `text` | NO | `'📦'` | 이모지 |
| `color_slot` | `smallint` | NO | — | 1~8. 자동 배정, 순환 |
| `deleted_at` | `timestamptz` | YES | `NULL` | 소프트 삭제 시각 |
| `created_at` | `timestamptz` | NO | `now()` | **칩 정렬 기준** |

```sql
PRIMARY KEY (id)
FOREIGN KEY (user_id) REFERENCES auth.users(id) ON DELETE CASCADE

CHECK (type IN ('income','expense'))
CHECK (char_length(name)  BETWEEN 1 AND 20)
CHECK (char_length(emoji) BETWEEN 1 AND 8)
CHECK (color_slot BETWEEN 1 AND 8)

UNIQUE (user_id, type, name)      -- 삭제된 것 포함
UNIQUE (id, user_id)              -- profiles 복합 FK 대상
UNIQUE (id, user_id, type)        -- transactions 복합 FK 대상

INDEX (user_id, type) WHERE deleted_at IS NULL
```

**설계 판단**

| | |
|---|---|
| `color_slot` 을 **읽지 않는다** | 통계 색이 순위 기반 램프로 바뀌면서 화면에서 쓰지 않게 됐다. 컬럼과 `create_category` 의 슬롯 배정은 나중을 위해 남겨 뒀다 (기획서 §6.3) |
| `color_slot` 에 유니크 없음 | 1~8 순환을 허용한다. 중복은 정상 상태다 |
| 이름 유니크에 부분 조건 없음 | 삭제된 것까지 포함해야 "되살릴까요?" 감지가 가능하다 |
| `emoji` 최대 8자 | 결합 이모지(`👨‍👩‍👧‍👦` = 7자), 국기(`🇰🇷` = 2자)를 허용 |
| `sort_order` 없음 | 칩 그리드 순서는 생성순 고정이라 `created_at` 으로 충분. `최근` 줄은 거래의 `created_at` 에서 따로 계산한다. **단 `created_at` 이 겹치면 정렬이 무의미해진다** — 아래 참조 |

> **`created_at` 하나로 정렬하면 순서가 흔들린다 (마이그레이션 0006 에서 고침)**
>
> `handle_new_user()` 가 기본 카테고리 10개를 한 INSERT 문으로 넣어서 `created_at` 이
> 전부 같은 값이었다. `ORDER BY created_at` 은 값이 같으면 순서를 정하지 못하고,
> Postgres 는 UPDATE 시 새 행 버전을 힙 끝에 쓰므로 **이모지 하나만 고쳐도 칩이
> 자리를 옮겼다.** 실측:
>
> ```
> 변경 전        교통 → 주거·통신 → 생활용품 → 문화·여가 → 식비 → 카페·간식
> 이모지 UPDATE  주거·통신 → 생활용품 → 문화·여가 → 식비 → 교통 → 카페·간식
>                                                     ↑ 교통이 1번에서 5번으로
> ```
>
> 기획서 §5.3 이 "위치가 고정돼야 안 보고 누른다"고 약속한 그 위치가 이미 안 고정이었다.
> 세 겹으로 막았다 — 시드가 1ms 씩 벌어진 타임스탬프를 갖고, `(user_id, created_at)`
> 유일 인덱스로 재발을 막고, 클라이언트 쿼리가 `id` 를 동순위 기준으로 함께 넘긴다.
> 마지막 것은 중복이지만 남겨 둔다. 결정성을 한 곳에서만 보장하면 그곳이 무너질 때
> 조용히 깨진다.
| 급여 플래그 없음 | `profiles.salary_category_id` 가 가리킨다 |

**이름 정규화** — 저장 전에 앞뒤 공백 제거 + 연속 공백을 하나로 압축한다. 안 하면 `'헬스 '` 로 유니크 제약을 우회해 사실상 같은 이름의 카테고리가 둘 생긴다.

### 2.4 `transactions`

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `id` | `uuid` | NO | `gen_random_uuid()` | PK |
| `user_id` | `uuid` | NO | — | 소유자 |
| `category_id` | `uuid` | NO | — | 카테고리 |
| `type` | `text` | NO | — | `'income'` \| `'expense'` |
| `amount` | `integer` | NO | — | 원 단위 **양수**. int4 상한이 2,147,483,647 이므로 입력을 **9자리로 끊는다** |
| `occurred_on` | `date` | NO | — | 거래 날짜 (시간 없음) |
| `memo` | `text` | YES | `NULL` | 최대 100자 |
| `created_at` | `timestamptz` | NO | `now()` | 같은 날짜 내 정렬 보조 |

```sql
PRIMARY KEY (id)
FOREIGN KEY (user_id) REFERENCES auth.users(id) ON DELETE CASCADE

FOREIGN KEY (category_id, user_id, type)
    REFERENCES categories (id, user_id, type)
    ON DELETE RESTRICT

CHECK (type IN ('income','expense'))
CHECK (amount > 0)
CHECK (memo IS NULL OR char_length(memo) <= 100)

INDEX (user_id, occurred_on DESC)
INDEX (category_id)
```

**3열 복합 FK가 세 가지를 한 번에 막는다**

| 막는 것 | 안 막으면 |
|---|---|
| 타입 불일치 | 지출 거래에 수입 카테고리가 붙어 월별 총수입·총지출이 통째로 틀린다 |
| 소유권 위반 | 남의 카테고리 id를 붙일 수 있다. **FK 검사는 RLS를 우회**하므로 이 제약이 필요하다 |
| 참조 무결성 | 거래가 있는 카테고리가 완전 삭제된다 |

**`amount` 는 항상 양수.** 부호는 `type` 이 결정한다. 음수를 허용하면 "지출 −5,000"이 실질 수입이 되는 경로가 생긴다.

**`occurred_on` 은 `date`.** `timestamptz` 로 두면 자정 근처 거래가 타임존 차이로 옆 달에 잡힌다. 날짜만 저장하면 그 문제가 존재하지 않는다.

**`updated_at` 없음.** 화면 어디서도 읽지 않는다. 남기려면 트리거로 서버 시각을 써야 하는데, 그렇게까지 해서 얻는 정보가 "고쳤다는 사실과 시각"뿐이라 디버깅 가치가 낮다.

## 3. RLS

세 테이블 모두 RLS를 켜고 정책 하나씩만 건다.

| 테이블 | 정책 |
|---|---|
| `profiles` | `FOR ALL USING (auth.uid() = id) WITH CHECK (auth.uid() = id)` |
| `categories` | `FOR ALL USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)` |
| `transactions` | `FOR ALL USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)` |

`FOR ALL` 하나로 SELECT/INSERT/UPDATE/DELETE가 덮인다. `USING` 은 읽기·수정 대상을 거르고 `WITH CHECK` 는 쓰는 값을 검증한다. **둘 다 있어야 남의 `user_id` 로 쓰는 것까지 막힌다.**

집계 함수는 `SECURITY INVOKER` 로 둔다. 호출자 권한으로 실행되어 RLS가 그대로 적용된다.

## 4. DB 함수

클라이언트가 하면 안 되는 것만 DB로 내린다. **삭제·복구·급여 지정은 함수가 필요 없다** — 단순 UPDATE 한 줄이고 RLS가 보호한다.

### 4.1 `handle_new_user()` — 가입 트리거

```
TRIGGER AFTER INSERT ON auth.users
  1. profiles 생성  (nickname = raw_user_meta_data->>'nickname')
  2. 기본 카테고리 10개 생성
  3. profiles.salary_category_id = '급여' 카테고리 id
```

**앱 코드가 아니라 트리거인 이유**: 가입 직후 앱에서 insert하면 그 요청이 실패했을 때 **카테고리가 하나도 없는 유저**가 생긴다. 앱은 그 상태를 가정하지 않아 깨진다. 트리거는 가입과 같은 트랜잭션이라 원자적이다.

닉네임은 `signUp()` 의 `options.data` 로 넘기면 `raw_user_meta_data` 에 담긴다.

이메일 인증을 켜도 `auth.users` 행은 인증 전에 생성되므로, 트리거는 인증 흐름과 무관하게 동작한다.

**기본 카테고리 시드**

| type | name | emoji | color_slot |
|---|---|---|---|
| expense | 식비 | 🍚 | 1 |
| expense | 카페·간식 | ☕ | 2 |
| expense | 교통 | 🚌 | 3 |
| expense | 주거·통신 | 🏠 | 4 |
| expense | 생활용품 | 🛒 | 5 |
| expense | 문화·여가 | 🎬 | 6 |
| income | 급여 | 💼 | 1 |
| income | 용돈 | 💰 | 2 |
| income | 금융수입 | 📈 | 3 |
| income | 기타수입 | 📦 | 4 |

시드 시점에만 이름으로 '급여'를 찾는다. 이후로는 id로만 참조한다.

### 4.2 `create_category(p_type, p_name, p_emoji)`

```
1. 이름 정규화 (trim + 연속 공백 압축)
2. 색 슬롯 배정 — 아래 쿼리
3. INSERT
```

**슬롯 배정**: 활성 카테고리가 쓰지 않는 슬롯 중 가장 작은 번호. 8개가 모두 쓰이고 있으면 가장 적게 쓰인 슬롯으로 순환한다.

```sql
SELECT s.slot
FROM generate_series(1,8) AS s(slot)
LEFT JOIN categories c
       ON c.user_id = auth.uid()
      AND c.type = p_type
      AND c.deleted_at IS NULL
      AND c.color_slot = s.slot
GROUP BY s.slot
ORDER BY count(c.id), s.slot
LIMIT 1
```

한 쿼리가 "빈 슬롯 우선"과 "순환"을 동시에 처리한다. 빈 슬롯은 `count = 0` 이라 자연히 먼저 뽑힌다.

**RPC인 이유**: 슬롯 조회와 INSERT가 원자적이어야 한다. 클라이언트에서 두 단계로 하면 동시 요청 시 같은 슬롯이 두 번 배정된다.

**이름 충돌 처리**: `UNIQUE (user_id, type, name)` 위반이 나면 앱이 그 이름의 삭제된 카테고리를 조회해 되살리기 다이얼로그를 띄운다. 별도 사전 검사가 필요 없다 — **제약이 곧 검사다.**

### 4.3 집계 함수 4개

| 함수 | 인자 | 반환 |
|---|---|---|
| `get_month_summary` | `p_month date` | `income`, `expense`, `net` |
| `get_category_stats` | `p_month date` | 카테고리별 `id, name, emoji, color_slot, total` (지출만, 내림차순) |
| `get_salary_widget` | **`p_today date`** | `salary_amount, salary_date, spent_since, remaining, upcoming, next_salary_date` |
| `get_recent_category_ids` | — | 마지막 사용순 `category_id` 목록 (최근 → 오래된) |

> **`get_recent_category_ids` 가 `max(created_at)` 으로 정렬하는 이유**
>
> `occurred_on` 은 사용자가 고른 거래 날짜다. 주말에 지난주를 몰아 적으면 방금
> 입력한 카테고리의 `occurred_on` 이 며칠 전이라 최근 목록에서 뒤로 밀린다.
> 사람이 "최근에 쓴 것"으로 느끼는 건 손이 마지막으로 누른 것 — 즉 `created_at` 이다.
>
> 타입 구분과 개수 제한은 하지 않는다. 화면이 이미 타입별로 걸러진 칩 목록을
> 들고 있어 교집합만 취하면 되고, 노출 개수를 바꿀 때 마이그레이션이 필요 없다.
> 이 순서는 칩 그리드가 아니라 그리드 위 `최근` 3칸에만 쓴다 (기획서 §5.3).

> **`get_salary_widget` 이 오늘 날짜를 인자로 받는 이유**
>
> Supabase 의 DB 타임존은 UTC 라서 `current_date` 가 KST 와 최대 하루 어긋난다 —
> 한국 시간 **오전 0~9시에는 '어제'를 가리킨다.** 그 시간대에 앱을 열면 오늘 쓴 돈이
> "월급 남은 돈"에 반영되지 않는다.
>
> 거래를 `date` 로만 저장해 타임존 문제를 없앴다고 봤지만, **"오늘이 언제인가"에는
> 여전히 남아 있었다.** 거래 입력 폼도 사용자의 로컬 날짜를 쓰므로 같은 기준을
> 써야 화면과 맞는다. 그래서 클라이언트가 자기 로컬 날짜를 넘긴다.

**RPC로 감싸는 이유**: PostgREST에서 `GROUP BY` 집계는 제약이 있고 쿼리 문자열이 지저분해진다. 함수로 두면 SQL이 한 곳에 모인다.

전월 대비는 별도 함수 없이 `get_month_summary` 를 이전 달로 한 번 더 호출한다.

### 4.4 함수가 필요 없는 작업

| 작업 | 구현 |
|---|---|
| 카테고리 삭제 | `UPDATE categories SET deleted_at = now() WHERE id = ?` |
| 카테고리 되살리기 | `UPDATE categories SET deleted_at = NULL WHERE id = ?` — **슬롯은 그대로 둔다.** 순환을 허용하므로 중복 검사가 없고, 따라서 과거 통계의 색이 항상 보존된다 |
| 급여 카테고리 지정 | `UPDATE profiles SET salary_category_id = ? WHERE id = auth.uid()` — 한 행 |
| 거래 CRUD | 일반 insert/update/delete |

## 5. 쿼리 로직

### 5.1 월 범위

```
start = date_trunc('month', p_month)
end   = start + interval '1 month'
조건  : occurred_on >= start AND occurred_on < end
```

`BETWEEN` 대신 `>=`, `<` 를 쓰면 말일 경계 실수가 없다. `occurred_on` 이 `date` 라 타임존이 개입하지 않는다.

### 5.2 월급 위젯

```
salary       = profiles.salary_category_id 카테고리의 거래 중
               occurred_on <= p_today 인 가장 최근 1건 (삭제된 카테고리면 제외)
spent_since  = SUM(amount) WHERE type='expense'
                 AND occurred_on BETWEEN salary.occurred_on AND p_today
remaining    = salary.amount - spent_since
upcoming     = SUM(amount) WHERE type='expense' AND occurred_on > p_today
next_salary  = salary.occurred_on + interval '1 month'
```

`p_today` 는 클라이언트의 로컬 날짜다 (§4.3 참조).

`+ interval '1 month'` 는 PostgreSQL이 말일을 자동 보정한다 (1/31 → 2/28). 별도 로직이 필요 없다.

`salary_category_id` 가 NULL이거나 해당 카테고리가 삭제 상태면 NULL을 반환하고, 앱은 빈 상태를 표시한다.

### 5.3 카테고리 통계

```sql
SELECT c.id, c.name, c.emoji, c.color_slot, SUM(t.amount) AS total
FROM transactions t
JOIN categories c ON c.id = t.category_id
WHERE t.user_id = auth.uid()
  AND t.type = 'expense'
  AND t.occurred_on >= start AND t.occurred_on < end
GROUP BY c.id
ORDER BY total DESC
```

**삭제된 카테고리도 그대로 나온다.** `deleted_at` 을 보지 않는 것이 "과거 통계 보존"의 구현이다.

상위 7개 + 기타 묶기는 **클라이언트에서** 한다. 기타를 펼치려면 전체 목록이 필요하기 때문이다.

### 5.4 거래 목록

RPC 없이 일반 select + join.

```
select : id, amount, type, occurred_on, memo, categories(name, emoji, color_slot)
where  : user_id, 월 범위, [type], [category_id]
order  : occurred_on DESC, created_at DESC
```

### 5.5 카테고리 필터 목록

**활성 카테고리가 아니라 "그 달에 거래가 있는 카테고리"로 채운다.**

```sql
SELECT DISTINCT c.id, c.name, c.emoji
FROM transactions t JOIN categories c ON c.id = t.category_id
WHERE t.user_id = auth.uid()
  AND t.occurred_on >= start AND t.occurred_on < end
```

활성 기준으로 채우면 삭제된 카테고리의 과거 거래를 필터로 찾을 방법이 없어진다 — 3월 내역에 '헬스' 거래가 보이는데 필터 목록에는 '헬스'가 없는 상태가 된다.

### 6.1 라우트

**거래 등록·수정 모달을 URL에 둔다** (`?new=1`, `?edit=<id>`). 뒤로가기로 모달이 닫히고 새로고침이 자연스럽게 동작한다.

**라우트를 `React.lazy` 로 나눈다.** 로그인 화면이 통계·거래 코드까지 전부 받아올 이유가 없다. 메인 청크 540kB → 487kB.

### 6.3 상태 관리

| 종류 | 담당 |
|---|---|
| 인증 세션 | `AuthProvider` (`onAuthStateChange`) |
| 서버 데이터 | TanStack Query |
| 선택한 월 · 필터 · 모달 | **URL searchParams** |
| 전역 클라이언트 상태 | **없음** |
| 직전에 저장한 날짜 | `TransactionFormSheet` 의 모듈 스코프 변수 |

Redux·Zustand가 필요 없다. 서버 데이터는 Query가, 화면 상태는 URL이 갖는다.

**날짜 하나만 예외로 모듈 스코프에 둔다.** 시트를 닫으면 컴포넌트가 사라지므로 `useState` 로는 다음 시트에 전달할 수 없고, URL 에 넣으면 주소를 공유했을 때 남의 작업 날짜가 따라간다. 새로고침하면 사라지는 것이 여기서는 **원하는 동작**이다 — 물려받은 날짜가 다음 날까지 살아남으면 오늘 지출이 조용히 지난주로 들어간다(기획서 §5.3).

### 6.4 쿼리 키와 무효화

키와 무효화 규칙은 `src/lib/queryKeys.ts` **한 파일에서만** 관리한다. 각 쿼리가 "무엇이 바뀌면 낡는가"를 표로 선언하고, 무효화 함수는 그 표에서 목록을 만든다.

| 키 | 거래 변경 시 | 카테고리 변경 시 | 비고 |
|---|:---:|:---:|---|
| `['categories']` | | ✓ | |
| `['profile']` | | ✓ | 급여 카테고리 지정 |
| `['recent-categories']` | ✓ | ✓ | 순서가 바뀌고, 삭제된 것은 빠져야 한다 |
| `['transactions', month]` | ✓ | ✓ | 행이 카테고리 이름·이모지를 쓴다 |
| `['transaction', id]` | ✓ | | |
| `['transaction-count', categoryId]` | ✓ | ✓ | 삭제·되살리기 안내 문구 |
| `['month-summary', month]` | ✓ | | |
| `['category-stats', month]` | ✓ | ✓ | |
| `['salary-widget', today]` | ✓ | ✓ | 급여 지정이 바뀌면 기준 자체가 바뀐다 |
| `['lifetime-net']` | ✓ | | |

접두사만 넘기면 TanStack 이 부분 일치로 월·id 가 붙은 키까지 잡는다 — `['transactions']` 하나로 2026-07, 2026-06 … 이 모두 무효화된다.

**이 표를 만든 계기는 실제 버그였다.** 무효화 목록이 두 파일에 나뉘어 있어 서로를 몰랐고, 카테고리 쪽에 `salary-widget` 이 빠져서 급여 지정을 옮겨도 위젯이 낡은 값을 계속 보여줬다. 아무 에러도 나지 않는 종류의 버그다. 그래서 목록을 한 곳에 모으는 데 그치지 않고, **빠뜨리면 컴파일이 안 되게** 했다 — 키를 만들려면 표에 항목이 있어야 하고, 표의 항목에는 `staleOn` 이 필수다.

### 6.5 라우트 가드

```
비로그인으로 보호된 경로 접근    →  /login
로그인 상태로 /login, /signup    →  /
세션 확인 중                    →  전체 화면 스피너
```

세션 확인이 끝나기 전에 렌더하면 **로그인 상태인데 로그인 화면이 깜빡** 보인다. 흔한 실수다.

## 7. 인증 흐름

### 7.1 가입

```
signUp({ email, password, options: { data: { nickname } } })
   → auth.users 생성 → 트리거가 프로필·기본 카테고리 생성
   → 세션 없음 (이메일 인증 켜져 있음)
   → 같은 화면에서 "메일을 확인해 주세요  [다시 보내기]" 로 전환
   → 메일 링크 클릭 → redirectTo 로 복귀
   → supabase-js 가 URL의 토큰을 자동 처리해 세션 생성 → 홈
```

**Supabase 대시보드에 Redirect URL 등록이 필요하다** — 로컬 `http://localhost:5173`, 배포 도메인. 등록하지 않으면 인증 링크가 엉뚱한 곳으로 간다.

### 7.2 로그인 실패 메시지

| 상황 | 메시지 |
|---|---|
| 비밀번호 틀림 / 없는 계정 | `이메일 또는 비밀번호가 올바르지 않습니다` |
| 미인증 계정 | `이메일 인증이 필요합니다` + **[인증 메일 다시 받기]** |

전자는 계정 존재 여부를 감추려고 통일한다. **후자는 예외다** — 통일하면 비밀번호가 맞는데도 계속 틀렸다고 나와서 사용자가 영원히 로그인할 수 없다.

### 7.3 비밀번호 재설정

```
/forgot-password   resetPasswordForEmail(email, { redirectTo })
/reset-password    (링크로 진입, 세션 자동 생성) → updateUser({ password })
설정 → 비밀번호 변경   updateUser({ password })
```

현재 비밀번호 재확인은 넣지 않는다. Supabase는 세션만 있으면 변경해 주고, 재확인을 구현하려면 `signInWithPassword` 로 한 번 더 검증하는 우회가 필요하다.

| 단계 | 내용 | 완료 기준 | |
|---|---|---|---|
| 1 | 프로젝트 셋업, Supabase 연결, 스키마 + RLS + 트리거 | 테스트 유저를 만들면 기본 카테고리 10개가 생김 | ✅ |
| 2 | 인증 (가입·메일인증·로그인·재설정·라우트 가드) | 가입 → 메일 → 로그인 → 홈 도달 | ✅ |
| 3 | 카테고리 CRUD (`create_category`, 삭제, 되살리기, 급여 지정) | 카테고리 관리 화면이 완전히 동작 | ✅ |
| 4 | 거래 CRUD + 내역 화면 (월 네비게이터, 날짜 그룹핑, 필터) | 기록하고 조회할 수 있음 — **여기서 실사용 시작 가능** | ✅ |
| 5 | 월별 요약 + 월급 위젯 | 홈 상단 완성 | ✅ |
| 6 | 통계 (스택 바, 가로 막대, 전월 대비, 누적) | 통계 탭 완성 | ✅ |
| 7 | 마무리 (데스크톱 레이아웃, 밀도, 코드 스플리팅, 비밀번호 변경) | | ✅ |

**4단계에서 이미 쓸 수 있었다.** 5~7이 늦어져도 앱은 제 역할을 한다.

7단계에서 실제로 한 일은 계획과 조금 달랐다. 빈/로딩/에러 상태와 스낵바는 각 단계에서 이미 만들어졌고, **대신 데스크톱 화면을 처음 열어보면서 나온 문제들**(FAB 이 목록을 덮음, 상단 탭 미구현, 컬럼 경계 없음)을 처리했다. 화면을 실제로 띄워 보지 않으면 안 보이는 종류였다.

### 8.1 검증

단계마다 브라우저를 실제로 띄워 훑었고, 그 스크립트를 `e2e/` 에 남겼다 ([e2e/README.md](../e2e/README.md)).

```bash
npm run test:e2e     # 통합 검증 67건 × 3회
npm run test:ux      # 사용성 — 탭 수와 마찰 측정
```

Playwright 러너를 쓰지 않고 스크립트 3개로 둔 것은 검증이 67개뿐이라서다. 설정 파일보다 스크립트 하나가 읽기 쉽다.

**단위 테스트가 없는 이유.** 이 앱의 로직은 대부분 DB 함수와 화면 조립이다. 순수 함수는 `lib/month.ts` 정도인데, 그마저도 실제 버그(타임존, 월말 경계)는 화면을 통과시켜 봐야 드러났다. 그래서 검증 예산을 통합 쪽에 몰았다.

**3회 돌리는 이유.** 한 번만 돌리면 경합을 못 잡는다. 같은 실패가 1/3 이면 경합, 3/3 이면 결정적 — 이 구분이 원인 추적의 출발점이다. 실제로 이 방식으로 앱 버그 6건과 테스트 결함 4건을 구분해 냈다.

## 9. 설계 중 확정한 사항 (기획서 갱신 반영)

| 항목 | 결정 | 근거 |
|---|---|---|
| 급여 카테고리 식별 | `profiles.salary_category_id` (id 참조) | 이름은 식별자가 아니다. 급여 여부는 카테고리 속성이 아니라 유저 설정이다 |
| 카테고리 개수 | 무제한, 색 슬롯 1~8 순환 | 시각 제약이 도메인 규칙을 정하면 안 된다 |
| 카테고리 삭제 | 항상 소프트 삭제 | 완전 삭제하면 실행 취소가 불가능해진다 |
| 이름 유니크 | 삭제된 것 포함 | 되살리기 감지에 필요 |
| 이름 정규화 | trim + 연속 공백 압축 | `'헬스 '` 로 유니크 제약이 우회된다 |
| 타입 일치 | 3열 복합 FK | 앱 로직이 아니라 DB가 강제한다 |
| `updated_at` | 없음 | 읽는 화면이 없다 |
| 필터 목록 | 그 달에 거래가 있는 카테고리 | 삭제된 카테고리의 과거 거래를 찾을 수 있어야 한다 |
| `get_salary_widget(p_today)` | 클라이언트가 오늘 날짜를 넘김 | DB 타임존이 UTC 라서 `current_date` 가 KST 와 하루 어긋난다 |
| 차트 라이브러리 없음 | `div` + CSS | 사각형 두 종류뿐. 축·툴팁·좌표 변환이 없다 |
| 통계 색 | 순위 기반 단일 색조 램프 | 이모지·이름이 정체성을 담당하므로 색은 순위를 나른다 |
| 데스크톱 탭 위치 | 컬럼 상단 (`sm:` 브레이크포인트) | 하단 고정 탭은 큰 화면에서 멀고, FAB 이 목록을 덮는다 |
| 라우트 코드 스플리팅 | `React.lazy` | 로그인 화면이 통계·거래 코드를 받을 이유가 없다 |
| `최근` 줄 정렬 기준 | 거래의 `max(created_at)` | `occurred_on` 은 사용자가 고른 거래 날짜라, 몰아 적기 시 방금 입력한 것이 뒤로 밀린다 |
| 재정렬 범위 | 그리드 위 3칸만 | 그리드까지 재정렬하면 오탭이 에러 없이 통계를 틀어뜨린다 |
| 물려받은 날짜 저장 위치 | 모듈 스코프 변수 | 새로고침하면 초기화되는 것이 원하는 동작. URL 이면 주소 공유 시 따라간다 |
| dirty 판정 기준 | `openedWith` (시트를 연 시점의 날짜) | `today()` 와 비교하면 물려받은 날짜 때문에 열자마자 "작성 중"이 된다 |
| 저장 후 그 거래의 달로 이동 | 보던 달에 머무름 | 지난달을 보는 중에 저장하면 목록이 비어 있어 저장 실패처럼 보였다 |
| 칩 정렬 = `created_at, id` + 유일 인덱스 | `created_at` 하나 | 값이 겹치면 UPDATE 한 번에 순서가 뒤집힌다 (0006) |
| 금액 입력 9자리 | 10자리 / `bigint` 로 변경 | int4 상한 초과가 22003 원문 에러로 화면에 떴다. 자리수로 막으면 입력 자체가 불가능해진다 |
